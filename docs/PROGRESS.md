# Reqo: Project Progress Log

Living document. Each release, decision, and verified fact is recorded here. Newest entries go at the top of the Changelog.

Status key: **[verified]** confirmed on chain or by a passing test. **[unverified]** assumed or read from docs, not tested. **[open]** unresolved.

---

## 1. Summary

Reqo is a memecoin launchpad on QoreChain testnet (Diana). Users create tokens from a web page, and the factory records each token and its creator.

- **v1** (Solidity, deployed): only the account holding an open EVM window can create tokens.
- **v2** (Solidity, deployed and tested): users sign a creation request off chain, and a relayer submits it. The signer is recorded as creator, so users need no window. Supply uses 18 decimals.
- **v2.1.0** (frontend and API): when the relayer window is closed, signed requests are queued and submitted automatically once it opens. The page shows the planned opening time and displays tickers with a `$` prefix.
- **v2.2.0** (API and frontend): token images. The image is uploaded to Vercel Blob, and its link is stored inside the on-chain description as `img:<url>`.
- **v2.3.1** (frontend fix): the image is read as soon as it is chosen and cached, so a file the browser has released no longer fails the launch. The exact browser read error is shown on the page.
- **v3 swap path** (contracts, verified on Diana): a trader signs a permit and a swap intent off chain, the owner relayer submits `swap`, and the trader receives tokens at or above the signed minimum. Replay, expired intents, and intents signed by another key are rejected.
- **v3 launch path** (contracts, live on Diana): WQOR, MemeTokenV3, PoolV3 and MemeFactoryV3 are deployed. A launch creates a token whose full supply and a 10 WQOR seed sit in a constant-product pool. Quote math and seeding are verified on chain.
- **v2.3.0** (frontend): Nearly-style mobile layout with Board, Launch, and More tabs, the Reqo logo, and coming-soon placeholders for features not yet built.

A real wallet with no window of its own has created a token through the v2 relayer (see section 5). Queued submission is built but not yet tested.

## 6. Relayer Architecture (v2.1.0)

| File | Role |
|---|---|
| lib/common.js | Shared config, EIP-712 domain and types, request validation, window check, queue storage helpers |
| api/relay.js | Accepts signed requests. Verifies signature, deadline, nonce. Submits now if the window is live; otherwise queues (202). Rate limit 5 per hour per address (in memory). |
| api/status.js | Window state, planned opening time, queue size. With `?id=`, the status of one request. |
| api/process.js | Scheduler. Requires `x-cron-secret`. Submits up to 5 queued requests per run, only while the window is live. Optional `?opensAt=` stores the planned opening time in KV. |
| index.html | Frontend. Signs requests, shows window banner, polls queued requests every 30 seconds, displays `$TICKER`. |

**Queue storage keys (Upstash):**
- `req:<id>`: JSON record with status (queued, submitted, expired, error), request, signature, txHash, error, deadline. Expires one day after the request deadline.
- `queue`: set of queued request IDs. The ID is the keccak hash of the signature.
- `config:opensAt`: planned opening time in ISO format, set through `/api/process?opensAt=`.

## 7. EVM Authorization Window (verified behaviour)

- A window is per account. It only permits transactions from that account.
- Opened from the Dashboard or QoreX, on an Ethereum (coin type 60) account. A standard qor1 (coin type 118) account cannot sign for its EVM address.
- Requires a registered ML-DSA-87 key. Registration and open/close use the PQ key. Transactions inside the window are signed by the normal EVM key.
- Query: `GET https://api-testnet.qore.host/qorechain/pqc/v1/evm_window/<qor1 address>`. Fields checked: `live`, `remaining_blocks`, `remaining_txs`.
- Limits observed: `blocks` up to 17,280 (about 6 hours on testnet), `max_txs` up to 1,000, `max_value` in uqor (counts value plus max fee). `native_only` false allows contract creation.
- Windows used for contract creation must not set `allowed-targets`.
- Windows expire on their own. There is no permanent window.
- **Verified:** a relayed `createTokenFor` succeeded using the owner's window, with a signer that has no window and no funds.
- **Verified:** a real wallet with no window created a token through the relayer while the owner window was live.

**Operating model (decided, D10):** the window is opened manually in QoreX at the planned time. The ML-DSA-87 key is never stored on Vercel.

## 12. Release Format

Each update follows this block, and each release adds an entry to the changelog in the same commit.

- **Version:** vX.Y.Z (patch for fixes, minor for features, major for contract changes)
- **File:** `reqo-vX.Y.Z.html` for the page, or `reqo-vX.Y.Z-contracts.md` for contract notes
- **Change:** one line
- **Commit:** `vX.Y.Z: short description`
- **Checks before push:** version string present in the file, diff size matches the change, no content from other projects
- **Checks after deploy:** version string present on the live page, `/api/status` responds
- **Docs:** this file is updated in the same commit, sections 2, 4, 5, 6, 8, 9, 10, and 11 as relevant

## 14. Swap Design (route A in use)

Swap is the next major feature. Two routes are possible:

| Route | Description | Trade-off |
|---|---|---|
| A. Factory-created pool | Each token gets a constant-product pool deployed by the factory, with liquidity from the creator. | Fully on EVM, testable with Remix and the existing scripts. Needs contract work and liquidity seeding. |
| B. Chain AMM module | Use QoreChain's native `amm` module, which the SDK exposes. | Possibly less contract work, but requires native transaction signing and a different frontend path. Unverified on testnet. |

Route A is in use: a constant-product pool created per token by the v3 factory. Route B was not pursued.
